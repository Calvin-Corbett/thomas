## Design tokens and the theme cascade

- THEME DEFINITION (CSS): thomas/server/web/css/tokens.css is the single token source. Nebula Core is the `:root` default (tokens.css:23-67, 20 `--c-*` colour tokens + `--c-danger/--c-warn/--c-success` + scrollbar tokens + `--font-*` + `--r-card/--r-composer`). The other four themes are attribute blocks on the html element: `html[data-thomas-theme="dark"], html[data-theme="dark"]` (tokens.css:70-82), light (84-96, sets `color-scheme: light`), aurora (98-111), sandstone (113-125, `color-scheme: light`, serif fonts). A legacy bridge `:root` block (131-195) aliases `--bg-app`, `--text-primary`, `--accent`, `--c-warning`, `--warn-bg` etc. onto the canonical set via var()/color-mix so any override of a `--c-*` token flows into the old names automatically.
- THEME DEFINITION (JS): thomas/server/web/js/chat_themes.js bakes the same five themes as `THEMES[name].vars` (lines 10-21, 20 keys each: the `--c-*` colour set incl. `--c-danger`/`--c-warn`, but NOT `--c-menu-bg`, `--c-success`, scrollbar, font or radius tokens) plus `THEME_META` (23-29: bot colours, trim, fontHead, fontLabel, rCard, rComposer, menuBg, composerAccent, msgRule, welcome copy). `deriveThemeVarsFromTokens()` (33-71) finds the FIRST stylesheet whose href contains '/css/tokens.css' (line 39), reads only rules whose selector starts with ':root' or matches `data-thomas-theme="(dark|light|aurora|sandstone)"` (49-53), and only for the 20 keys of THEMES.nebula.vars (35, 55-58); if any key is missing on :root it returns null and the baked payload stays (60-62). On success it REPLACES each THEMES[name].vars with the derived set (81) and warns on drift (83-85). THEME_META is never derived: fonts, radii, menu background, bot colours and welcome copy are a second, JS-only source of truth.

Risks / unverified:

- An overlay expressed only as CSS token blocks (the tokens.css pattern) will visibly work on settings/mission/classic but silently NOT change the chat shell or any tab document, because chat.html paints THEMES vars inline on #tc-shell (chat.html:537) and workspace_shell paints them inline on html (workspace_shell.js:33-37); inline beats the sheet. Verification on /settings alone would pass while / stays stock.
- chat_themes.js derivation is keyed to a single sheet whose href contains '/css/tokens.css' and to exactly the 20 keys of THEMES.nebula.vars; an overlay sheet with a different path is ignored, and an overlay that removes or renames a key on :root makes derivation return null so the baked fallback silently takes over (chat_themes.js:39, 60-62).
- THEME_META (fonts, radii, menu background, bot colours, welcome copy) is baked in JS and reapplied AFTER vars (chat.html:543-545); overlay changes to --font-head/--r-card/--c-menu-bg via any CSS path are overwritten on the shell. A deliberate overlay has to cover this second source or fonts/radii cannot be re-themed.
- Per-tab: every tab is its own chat.html document (DOC_URL '/?embed=1&browser=0'), and theme sync between tabs is by clicking each document's own switcher (browser_shell_docs.js:346-361). An overlay applied only from the home document, or one that alters the switcher's option order/labels, breaks that relay (pickTheme matches by option index or label text).
- Serving overlay files under /static/ inherits the production immutable one-year cache (app_middleware_handlers.py:150-153); reusing the stock ?v= fingerprint (which hashes only stock files) means an edited overlay never reaches the browser until the stock build changes. The overlay needs its own version stamp (manifest revision) or a no-store route.
- New routes are blocked by the app_routes_init.py size (1471 lines vs python_hard 1200, not baselined). Either the overlay file route is hosted in an already-registered module (e.g. register_work_dashboard_routes, which already owns /api/ui/redesign) or static_compat's base_dirs (app_routes_init.py:1395) must change, which the guard may refuse.
- The existing 'make it real' path (ui_redesign_runtime.py:366-376) instructs Code to edit stock files in thomas/server/web/. Until it is redirected, the first Redesign action still produces base-file edits, which is the exact collision phase 4 is meant to prevent.
- Companion, frontier and system_map pages do not load workspace_shell.js, so a client-side injector there leaves those pages unthemed by the overlay; a server-side injection in build_page_handlers only covers /, /classic, /settings, /companion, and mission/my_stuff are served from app_routes_init.py.
- Theme-name whitelists in workspace_shell.js:4, chat_themes.js:43/51/64, settings.script01.js:76-79 and chat.html:533 coerce unknown names to 'nebula'; an overlay that adds a new theme name will be silently reset on reload, on storage events and on iframe relay unless all lists are extended (chat.html cannot be edited, so its loadTheme must accept whatever THEMES the overlay injects before line 446 runs).
- Layout edits already live in per-browser localStorage ('thomas_ui_layout_v2'), invisible to the server and to other tab documents; if the overlay manifest does not absorb them, a user's restyled elements exist in two incompatible stores.
- settings.style01.css and mission.style01.css declare their own literal semantic tokens (--c-danger/--c-success/--c-warning/--c-menu, fonts, --r-card) on :root and html[data-theme]; an overlay that overrides tokens.css values will not change those pages' semantic colours unless it also targets those names.
