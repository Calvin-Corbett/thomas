=== WHAT WAS WRONG (BEFORE FIXES) ===

1. SOUL.md — STALE DELEGATION MODEL
   The "Brain Protocol" section said:
     "Never execute directly — delegate to swarm agents"
     "shell.exec('python -m thomas.agent.swarm {task}')"
   
   This is WRONG. Thomas executes tools directly every session. The swarm system
   (thomas/agent/swarm.py) exists but is NOT the default path — it's for explicitly
   multi-agent tasks. Any AI reading the old SOUL.md would be confused about whether
   to delegate or just do the work. The swarm invocation command was also stale/wrong.

2. AGENTS.md — STARTUP LIST TOO LONG + MISSING VERSIONING RULE
   The startup file list included docs/ROUTING_FLOWCHART.md and docs/PROJECT_SCOPE.md.
   These are project documentation, not agent guidance files. Loading them at startup
   adds noise without value.
   
   Also: no rule existed telling Thomas to bump the version and update CHANGELOG.md
   when shipping changes. This is why the changelog was always stale.
   
   Also: "Telegram is a channel for Thomas, not a separate persona" was oddly specific
   for a general instructions file — Telegram is one integration, not a core identity rule.

3. windows_auth.py — SUSPICIOUS PROMPT PATTERNS CAUSED FALSE POSITIVES
   The original 17 patterns were too loose. Examples of normal developer instructions
   that would have triggered the Windows PIN dialog:
   
     - "respond only in valid json"       <- flagged by r"respond\s+only\s+in\s+valid\s+json"
     - "level 5 autonomy"                 <- flagged by r"level\s*5\s*autonomy"
                                             (this phrase is in Thomas's own SOUL.md!)
     - "verbatim instruction"             <- flagged by r"verbatim.*instruction"
     - "show custom instruction"          <- flagged by r"show.*custom.*instruction"
     - "bypass policy"                    <- too broad, catches legitimate discussion
     - "ignore previous instruction and"  <- catches normal conversation
   
   The gate would have been blocking the user's own legitimate requests constantly.

4. windows_auth.py — WRONG WINDOWS API
   The dialog uses CredUIPromptForCredentials, which shows a username+password box.
   For a real Windows Hello PIN prompt, the correct API is:
     CredUIPromptForWindowsCredentials with CREDUIWIN_AUTHPACKAGE_ONLY
   This requires pywin32 >= 228. Not fixed yet — noted as a future improvement in code.

5. windows_auth.py — SILENT FAILURE IF pywin32 NOT INSTALLED
   The except block in the gate call in loop.py catches all exceptions at DEBUG level:
     except Exception as e:
         log.debug("Suspicious prompt gate check failed (non-fatal): %s", e)
   If pywin32 isn't installed, the gate silently does nothing. No protection, no warning
   visible to the user. This is a known limitation — acceptable for now since the gate
   is defense-in-depth, not the primary security boundary.

6. versioning.md — GOOD RULES, ZERO COMPLIANCE
   The rule says bump pyproject.toml + thomas/__init__.py for every behavioral change.
   Multiple features had shipped without version bumps. No enforcement mechanism exists.

=== QUESTIONS FOR GROK ===

1. The suspicious prompt gate fires on the user's own messages (not just external API callers).
   Is this the right threat model? If the user is the only one sending prompts, the gate
   only protects against someone else at the keyboard — which Windows auth already handles.
   Should the gate be moved to the API boundary instead (only fire for remote/unauthenticated requests)?

2. The gate calls gate_suspicious_prompt() which calls check_prompt_suspicious() AGAIN
   (double-check). The loop.py code already called check_prompt_suspicious() to decide
   whether to yield the SECURITY_FLAG event, then calls gate_suspicious_prompt() which
   re-runs the check internally. This is redundant. Should gate_suspicious_prompt() accept
   a pre-computed (is_suspicious, matched) tuple to avoid the double regex scan?

3. SOUL.md now says Thomas executes directly. But the swarm system exists and is partially
   built. Should we document a clearer trigger for when to use swarm vs direct execution?
   Current guidance is vague: "explicitly multi-agent in scope."
