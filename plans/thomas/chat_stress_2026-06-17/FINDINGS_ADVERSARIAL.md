## 3. ToolSpecialist replaces the issued capability token's allowed_tools with the FULL registered tool set, nullifying per-specialist tool gating

- **Severity:** high · **Slice:** delegated-safety · **Dimension:** capability token tool gating / deny-unguarded-tools
- **Mechanism:** The orchestrator issues a CapabilityToken scoped to the specialist's declared capabilities (brain.py:977-983: allowed_tools=specialist.capabilities). For the tools specialist those are coarse category tags ('filesystem','shell','tool_execution',...), not concrete tool names. Instead of mapping categories to a permitted concrete-tool set, ToolSpecialist._execute_impl discards the scope entirely: it builds exec_token = replace(token, allowed_tools=registered) where `registered` is EVERY tool name returned by self.tools.list_tools() (tools.py:194-199). _run_tool's only gate is token.permits_tool(tool_name) (base.py:253), and permits_tool returns True whenever tool_name is in allowed_tools (protocol.py:85-89). Net effect: the LLM-emitted tool plan can name ANY registered tool — shell.exec, fs.write_file, git mutators — and it will always pass the permission check, because the token was just rewritten to permit all of them. The capability scope the orchestrator computed for this specialist is never enforced; the only residual guards are each tool's own internal sandbox/config flags (e.g. ShellTool._allowed, _safe_path), not the delegation token. The code comment claims 'the registry is the security boundary — only sandboxed-safe tools are registered', which silently downgrades a per-delegation scoping mechanism to 'whatever is installed is allowed'.
- **Evidence:** thomas/marketplace/orchestrator/brain.py:977-983 — token = CapabilityToken(specialist_id=..., allowed_tools=specialist.capabilities, ...); contract also sets allowed_tools=specialist.capabilities (line 963). thomas/marketplace/specialists/tools.py:128-139 — ToolSpecialist.capabilities returns coarse tags {"tool_execution","file_operations","system_info","data_processing","engineering","automation","filesystem","shell","project_stats"}, never concrete tool names. thomas/marketplace/specialists/tools.py:193-199 — exec_token=token; registered={str(getattr(t,"name","") or "") for t in self.tools.list_tools() if getattr(t,"name","")}; if registered: exec_token=replace(token, allowed_tools=registered). thomas/marketplace/specialists/base.py:253 — `if not token.permits_tool(tool_name):` is the only delegation gate in _run_tool (permits_action never called). thomas/marketplace/orchestrator/protocol.py:85-89 — permits_tool: `if not self.allowed_tools: return True; return tool_name in self.allowed_tools`. thomas/tools/registry.py:146-156 — registry.execute does no token/capability check, just get(name)+safe_execute; no permits_tool/allowed_tools references anywhere under thomas/tools. thomas/tools/shell.py:56 — name="shell.exec" (real registered tool; internal git-topology guard at shell.py:40-52 is its own residual sandbox, independent of the delegation token). thomas/server/routes/chat_v2.py:308-318 — ToolSpecialist registered with the shared `tools` registry into the live chat brain.
