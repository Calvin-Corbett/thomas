### Fixed

- **Certification checked the claim, not the thing claimed.** It required a `healthcheck` capability at a 95% pass rate and compared that against the manifest's *declared* capability list — nothing more. Every one of the 480 deleted packs listed `healthcheck` while its `hooks.py` defined only `before_tool`/`after_tool`, so all 480 certified and carried the rate over its bar without a single one implementing the thing being certified. A capability that is verifiable is now verified: the pack's declared entrypoint is loaded, `healthcheck` must be callable, calling it must not raise, and it must answer with a mapping carrying `ok`. A pack built to the exact shape of the deleted ones is now refused with the reason named — "declared but not implemented: healthcheck (no callable healthcheck in the entrypoint)".

- **The summary says how much of its own verdict it actually checked.** `verified_by_execution` counts packs whose capability was confirmed by running it; `declared_only` counts those still taken on faith because no verifier exists for that capability yet. Capabilities like `inkwell.notes` are feature namespaces with no executable form, so they remain declarations — but they are now reported as declarations instead of being silently folded into a pass rate. Without that split the next unverifiable capability would inflate the number exactly as the packs did. All five real extensions currently certify with `verified_by_execution: 5, declared_only: 0`.

- **Certification is now the one thing in the tree that loads pack code.** Verifying an implementation is impossible without running it. This is safe here because certification only ever walks `extensions/`, which is first-party bundled code; a load or call that fails is reported as "not implemented" rather than crashing the scan.
