### Removed

- **The multi-vendor e-commerce engine at the root of `thomas/marketplace/`, and the nine `marketplace.*` tools it put in front of every model on every boot.** You asked us to "make sure your codebase doesn't look stupid and full of junk", starting with the modules generated in the 2026-03-23 burst that are reachable only because the registry imports them at startup. Its entry was the last one in the boot table pointing at a module at the top level of `thomas/marketplace/` — every other surviving entry that loads marketplace code loads a subpackage. Twelve modules are gone — `vendors`, `listings`, `orders`, `payments`, `reviews`, `search`, `recommendations`, `analytics`, `disputes`, `tools`, `_types`, `_exceptions` — along with six module-only tests (`tests/test_marketplace_{vendors,listings,orders,payments,reviews,search}.py`, each headed "Tests for <name> module"). `register_marketplace_tools` made exactly nine `registry.register(...)` calls, so the boot table drops from 28 active entries to 27 and the registry a boot builds is nine tools smaller. The nine that disappear from what a model is offered are these: `marketplace.register_vendor`, `marketplace.get_vendor`, `marketplace.create_listing`, `marketplace.get_listing`, `marketplace.publish_listing`, `marketplace.create_order`, `marketplace.get_order`, `marketplace.create_review`, `marketplace.search_listings`.

- **None of those nine could complete a call: every one of them raised `ImportError`.** `thomas/marketplace/tools.py` imported `VendorManager`, `ListingManager`, `OrderManager`, `ReviewManager` and `SearchEngine` from its sibling modules. No such classes exist — those modules define `VendorRegistry`, `ListingRegistry`, `OrderProcessor`, `ReviewRegistry` and `SearchIndex`. The import sat inside `execute()` at `thomas/marketplace/tools.py:29`, above that method's `try:` at `:32` (line numbers as of `8f931035`, the base this change was made from), so the failure was never even caught and turned into an error string: `ImportError` came straight back out of `execute()`, for all nine tools, on any call. Nine tools were offered to every model on every boot and none of them could have done anything. Being reachable from the registry was mistaken for being used.

- **`thomas/marketplace/__init__.py` re-exported sixteen dataclasses that nothing imported.** `from thomas.marketplace import` appears nowhere in this repository — not in `thomas/`, `tests/`, `scripts/`, or `extensions/`. The package is now a docstring that names what is actually wired underneath it.

- **Nothing outside this change wires the twelve modules in, and no work in flight names them.** Grepping the classes the twelve modules actually define — `VendorRegistry`, `ListingRegistry`, `OrderProcessor`, `PaymentProcessor`, `ReviewRegistry`, `SearchIndex`, `RecommendationEngine`, `AnalyticsEngine`, `DisputeRegistry`, `EscrowManager`, `ShoppingCart`, `MarketplaceException` — across the `.py` files of `thomas/`, `scripts/`, `extensions/` and `tests/`, outside `thomas/_archived/`, finds one file: this change's own test, which names `VendorRegistry`, `ListingRegistry`, `OrderProcessor`, `ReviewRegistry` and `SearchIndex` in its docstring and imports none of them. No import line outside `thomas/_archived/` names any of them; the archive's own, unrelated `ShoppingCart` and `PaymentProcessor` classes share two of the names. (The names `tools.py` tried to import — `VendorManager`, `ListingManager`, `OrderManager`, `ReviewManager`, `SearchEngine` — were never defined in the engine, so grepping those proves nothing either way.) `thomas/marketplace/MANIFEST.json` names none of the twelve, because its plugin-content list only ever covered subpackage directories. Nothing under `plans/thomas/` claims any of them as work in progress either. There are two mentions, and neither is a claim on the code: a bulk semicolon-separated path enumeration at `plans/thomas/tasks/chat-code-work-convergence-2026-07-13/CHAT_CODE_WORK_BUILDOUT_LINE_ITEMS.md:259`, which lists paths and calls nothing; and decision D8 in the log at `plans/thomas/PRODUCT_READY_PUSH_2026-07-15.md:128`, which asked for the opposite of a claim — "E-commerce `marketplace.*` agent tools (register_vendor w/ tax_id+bank_account into unwired local store) unregistered by default (default: unregister until real backend exists)". That decision was recorded on 2026-07-15 and still listed as pending; the registration survived it by ten weeks. This change carries it out and goes one step further, because a backend never arrived and the tools could not run at all. The cross-branch scan ran: every branch tip in this clone — `dev` and the sixteen `origin/*` branches, including the eight `praxis/*` lines and `integration/unify-2026-08-14` — was grepped for `thomas.marketplace.tools`, `marketplace.register_vendor`, and a `from thomas.marketplace.<removed module> import` line, and every branch returns the same nineteen files: the engine's own eleven (the package `__init__.py` plus ten of the twelve modules — `_types.py` and `_exceptions.py` import no sibling, so they match no pattern), its six tests, and the two files this change edits. No branch adds a caller the tree does not already have, so nothing waiting for approval elsewhere wires this in. The one file another Thomas project has open that this change also touches is `thomas/server/chat_tool_policy_model.py`, where the edit is nine deleted lines in two sorted sets and nothing else, so the two merge cleanly. What guards the eighteen paths today is the ratchet test below, and only that: it fails by filename on any merge that brings one of these paths back, rather than letting it land quietly.

- **All nine names are out of the runtime capability tables, so no later tool can inherit a grant from a dead one.** A name left in `_WRITE_TOOLS` or `_SAFE_READ_TOOLS` after its module is gone is a grant sitting in wait for whatever future tool reuses the name, and all nine were there. `thomas/server/chat_tool_policy_model.py` carried five of them in `_WRITE_TOOLS` — `marketplace.create_listing`, `.create_order`, `.create_review`, `.publish_listing`, `.register_vendor` — and four in `_SAFE_READ_TOOLS` — `.get_listing`, `.get_order`, `.get_vendor`, `.search_listings`. Both blocks are deleted; the file's only surviving `marketplace` mention is a comment about `thomas/marketplace/specialists/`. No prefix rule needed changing, and that is worth recording: `marketplace.` is not in `_WRITE_PREFIXES`, `_EXTERNAL_PREFIXES`, `_CHANNEL_PREFIXES`, or `_SAFE_READ_PREFIXES`, so these nine were the whole of what the policy said about `marketplace.*`, and deleting the nine lines leaves the namespace with no standing grant at all. Ten marketplace subpackages still register tools at boot — `paper_trading` by its full `thomas.marketplace.` path, `asset_studio`, `orchestrator`, `realtime`, `security`, `vision` and `webhooks` through the `thomas.marketplace.` fallback in `_try_import`, and `channels`, `nodes` and `policy` directly, through their backward-compatible bridge packages (`thomas/channels`, `thomas/nodes` and `thomas/policy` add `thomas/marketplace/<name>` to their `__path__`) — and none of their classifications is touched. `paper_trading`'s, which live in this file, stay as they were: `paper_trading.propose`, `paper_trading.recall`, `paper_trading.review`, `paper_trading.submit` in `_WRITE_TOOLS`, and `paper_trading.` in `_EXTERNAL_PREFIXES`.

- **The eighteen files are unlinked; their graveyard records are still owed.** Nothing stands at any of the eighteen paths now, and each is staged as a deletion rather than as an emptied file — `git status` shows `D` for all eighteen, so the commit records a removal and not an eighteen-file truncation to zero bytes. This change does not add the death records: `docs/ops/graveyard.json` has none for any of the eighteen paths. Until someone runs one `scripts/forge/graveyard.py record-file` per path, `merge_resurrection_gate.py` treats a restored path as an ordinary add and passes it, and only the ratchet test below catches it. Landing also needs one `scripts/create_verification_record.py` run carrying both a shrinkage reason and a scope reason, because `shrinkage_gate.py` compares each staged code file against its `HEAD` line count and a deleted file measures as all of it removed, well past the 30% threshold, while `commit_scope_gate.py` asks for a scope justification above twenty staged code files (`WARN_THRESHOLD = 20`, `commit_scope_gate.py:30`) and this change's own code files number twenty-two: the eighteen deletions plus `thomas/server/tool_extensions.py`, `thomas/marketplace/__init__.py`, `thomas/server/chat_tool_policy_model.py`, and the new test. That is under the gate's `HARD_LIMIT = 50` and well under the sixty-file ceiling this piece was asked to stay inside. The three Markdown files it also touches — this fragment, `thomas/marketplace/STATUS.md`, and `plans/thomas/THOMAS_CODEBASE_ISSUE_QUEUE.md` — are not code by that gate's `CODE_EXTENSIONS`.

### Added

- **`tests/test_marketplace_commerce_engine_is_gone.py`.** A deletion a merge can undo is not a deletion. It asserts `thomas.marketplace.tools` is out of `_OPTIONAL_TOOL_MODULES` while `thomas.marketplace.paper_trading.tools` stays in it, that none of the nine tool names appears in any `chat_tool_policy_model` capability table, that the package re-exports no commerce type, and that `surface_policy.classify_marketplace_row` — the function the live `/api/marketplace/*` route calls — still imports. The installable-plugin marketplace (`extensions/`, `/api/marketplace/*`, the store UI) never depended on the deleted engine and is untouched.

- **A ratchet against the engine coming back.** Two tests hold the eighteen paths empty of anything. `test_nothing_stands_at_any_removed_path` fails and names the file the moment one of them exists again, so a merge cannot quietly restore the engine, and it counts a zero-byte file as back, because the next commit would fill it. `test_a_removed_module_cannot_be_imported` asks the import system for each of the twelve module names and requires all twelve to be unresolvable. `find_spec` answers from `sys.modules` for a name already imported, so that test holds only while nothing earlier in the session imports one of the twelve; the path test does not depend on that.
