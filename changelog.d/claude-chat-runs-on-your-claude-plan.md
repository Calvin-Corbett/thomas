### Added

- **Chat runs on your Claude plan, the same way Build does.** Build has driven the Claude Code CLI since 2026-09-24, so it needed no Anthropic API key; Chat could only reach Anthropic's API, which does. With your ChatGPT allowance spent, that left Chat unable to answer at all: "My ChatGPT limit ran out, so your Chat can't answer at all until Saturday, even though you can build on my Claude plan through Claude Code." Chat now runs the same CLI. Pick Claude Opus, Sonnet or Haiku in the model menu and the turn goes through your Claude Code sign-in, streaming as it is written. The conversation is sent as one labelled prompt (the CLI takes no message list), an attached image is named in place rather than dropped, and a tool call the model writes as JSON is turned back into a real tool call. The CLI's own Read, Write, Edit and Bash are all denied and the CLI is given no project directory: a chat turn answers, it does not act on this machine, and Thomas's own tool policy stays the only way a turn reaches a tool.

### Changed

- **Claude models are no longer hidden from the Chat model menu.** They carried a `build_only` mark because only Build could run them, and they read "needs key" because the Anthropic profile has none. The mark is gone, and the profile now shows "your Claude plan" and is selectable. It is offered only when the Claude CLI is actually installed, so nothing appears that cannot run, and adding an Anthropic key in Settings sends the same profile back to Anthropic's API. Build still lists only what its two engines can execute. The choice also survives a reload: Chat's start-up kept a second rule about which connections can answer, one that knew only about a stored key, so a Claude plan picked in the menu was swapped for another model the next time the page opened. Both now read the same rule.

### Fixed

- **A usage limit says which limit, when it resets, and what you can use instead.** Asked for a meal-prep plan on a plan limit with a day and a half left to run, Chat answered "The selected model is temporarily rate-limited. Please wait a moment or choose another model." You wrote: "The limit lasts until Saturday morning, not a moment, and there was no other model I could choose." Chat now reads the provider's own refusal and says, for example, "Your ChatGPT Pro plan has reached its usage limit — it resets Saturday 26 September at 08:02. This is not a wait of moments. I can answer on Claude Sonnet (newest) or Qwen2.5 Coder meanwhile — pick one from the model menu above the message box." The models named are the ones that answered at the catalog's last check, not everything configured, and when nothing else on the machine is ready it says that instead of offering a choice. A genuine short burst is still called a short burst, with the seconds it clears in. A 429 that names no provider claims nothing about how long it lasts.
- **The second message on a usage limit is told what the first one was.** After a refusal, the model profile is parked for a few minutes so the next message does not go out and be refused again — and while it is parked, the turn fails against the park rather than against the provider. The park is capped at ten minutes; the limit you met lasted a day and a half. So the first message could name the limit and its reset, and every message after it fell back to a sentence that named neither: "wait a moment", the words you wrote in about. The park now keeps the provider's own refusal and repeats it, so the limit, its reset and what you can use instead read the same on the second message as on the first. A park with nothing remembered still claims nothing. A task refused by that park was told the same thing a third way: a refusal with no usage-limit facts on it is treated as a burst to sit out, so the work announced "the provider asked Thomas to pause for 5.0s; work will resume automatically" and then asked again — seconds offered where the wait was a day and a half. The park hands back the usage-limit code and the reset time the provider's refusal carried, so a spent allowance is reported rather than waited out, and Autopilot's pause reads the limit out of a parked turn as it does out of a refused one. A wait that really is seconds long is still simply waited out.
- **The countdown under the message box no longer promises a spent allowance back in minutes.** A parked model is announced there as "gpt-5.6-sol is rate-limited · back in 9:58 · Thomas will try again when it clears" — a clock ticking down the park, which lasts ten minutes at most, while the allowance behind it was out until Saturday. "Please wait a moment", with no words in it. The line now reads the refusal the park remembers and, when the account is genuinely out of allowance, names the limit and its reset instead of counting: "ChatGPT Pro has reached its usage limit · resets Saturday 26 September at 08:02 · another model is needed until then", or the model that answered instead when one did. It stays up until that reset rather than disappearing when the park lifts, a reset the provider did not give is not invented, and a real short burst is still a countdown. The reset is worded in the same one place the chat message words it, so the two cannot disagree. The line is also told about a limit that began before the page did: the list it reads was the parks alone, so it held nothing eleven minutes into a limit that ran until Saturday, and Chat opened at any point over the rest of that day showed an ordinary composer with nothing to say about the model it was about to refuse you on. An allowance that is out is now reported for as long as it is out, with no park left to count, and the page asks when it opens rather than only after a turn has already failed.
- **What you can use instead is only ever something you can actually pick.** The sentence that names the way out — "I can answer on Claude Sonnet (newest) or Qwen2.5 Coder meanwhile" — is read from the model catalog's last check, and listing a connection's models costs no allowance: a plan that is out until Saturday answers that check exactly as it did before. Now that Chat runs on your Claude plan, a Claude limit would therefore have replied "I can answer on GPT-5.6 Sol meanwhile" and sent you back to the allowance you started from — "there was no other model I could choose", one limit later. A connection the refusal parked is no longer named, and is named again as soon as that park lifts. The catalog also carries each connection's declared model beside the models it listed, while the menu shows the declared one only when a connection listed none — your Claude plan declares one of Anthropic's versioned ids and offers Opus, Sonnet and Haiku — so a name the menu will not show is not offered either. What is named is a model that is in the menu and can answer when you pick it.
- **A plan stays off that list for as long as it is actually out.** Knowing a connection cannot answer was read from the park Thomas puts a refused model profile in — and a park set by a rate limit is capped at ten minutes, while the allowance behind it was out until Saturday. So the sentence naming the way out went back to offering your spent ChatGPT plan eleven minutes after it refused you: "there was no other model I could choose", once more, a little later. The question is now asked with the reset the provider gave as its lifetime instead of the park's, and only until that reset — a short burst, a refusal that named no reset, and a wait given only as a duration rather than a clock time (a duration runs from the refusal, so read later it would move further off every time and never arrive) all claim nothing and hide nothing, because hiding a model that can answer is the same falsehood facing the other way. The other half of this: your Claude plan was the one engine whose refusal never reached the park at all. The three HTTP connections hand their limit to it as they raise it; the Claude CLI did not, so a Claude plan limit left the countdown under the message box blank and let the way-out sentence keep offering the plan that had just refused the turn. It hands over the same words now, so the limit reads the same on the plan you asked for as on the one you were out of.
- **A plan that answers again stops being called out of allowance.** The change above reports a spent plan until the reset its refusal named rather than until the ten-minute park lifts, which leaves answering as the only thing that can end that claim early — and it does end early: a reset read from the Claude CLI's printed words is put an hour late on purpose when the time zone cannot be read here, and a provider can lift a limit whenever it likes. Coming back from a limit was recorded in one place only, the failover loop's success, and one plan picked in the model menu has no fallback to fail over to, so it took the other path and nothing recorded anything. Saturday morning, then: your plan answers your first message and the line under the composer still reads "has reached its usage limit · resets Saturday 26 September at 08:02" directly above the reply, and the sentence naming what you can use instead still leaves that plan out. A turn that answers now clears what the refusal left behind, on both paths. The page holding that line had the same hole from the other side: it asked the server about limits when it opened and after a failed turn, and never again, so a line good until Saturday stayed up for the rest of the session no matter what answered. A turn that goes through now takes down the line naming the plan that answered it, and asks the server what is still out.
- **A Claude plan with no sign-in is not named as the way out either.** The models offered instead of a limited one are the ones that answered the model catalog's last check, and for every connection but one that check spends the credential: a stale key or an expired sign-in is recorded there, and the connection is not offered. Your Claude plan is the exception, because listing what it offers is a constant — Opus, Sonnet, Haiku — and asks the Claude CLI nothing. So a ChatGPT limit could answer "I can answer on Claude Sonnet (newest) meanwhile" while the CLI on this machine had no sign-in to answer with: the sentence you wrote in about, under another provider's name. A turn the CLI refuses for want of a sign-in is now remembered, and that plan is left out of the list until it answers again — signing in through `claude` in a terminal is enough, with no restart.
- **Only a model your Claude plan offers starts the Claude program.** The first cut of this routing asked one question — is this Anthropic with no key? — and sent every such request through the Claude CLI, including requests that named one of Anthropic's own versioned model ids and meant the API. Picking Claude Opus, Sonnet or Haiku is what runs the CLI now; those three names are the whole of what the plan offers in the menu and the whole of what the transport accepts, built from one list so they cannot drift apart. An Anthropic profile on a versioned model with no key still goes to Anthropic's API, and is refused there for want of a key, which is the truth of it.
- **An Anthropic key problem is no longer reported as your ChatGPT sign-in.** Every unauthorized model call was answered with "Your ChatGPT sign-in has expired... Run `codex login` in a terminal" — a different product, and a command that cannot touch an Anthropic key. It is reachable from the change above: a Claude connection on one of Anthropic's versioned model ids goes to Anthropic's API and is refused there. Chat now reads which provider refused before it says whose sign-in it was, and for Anthropic says the key is missing or no longer valid, that `codex login` will not fix it, and that your Claude plan answers without a key wherever Claude Code is signed in. A 401 that names no provider still gets the ChatGPT sentence, which is the sign-in Thomas can restore. The health check said the same thing in the same breath — every unauthorized call was filed as a rejected ChatGPT sign-in, and the status page then reported "no model can be reached", which is not true while your Claude plan is installed and answering. Only the ChatGPT sign-in is filed there now, because that is the only credential that page can name or restore.
- **A Claude turn that cannot start says why, and on which surface.** Two ways of failing to start the CLI used to end as "I couldn't get an answer from the selected model": a surface whose event loop cannot run a subprocess at all (the terminal REPL asks for one of those on Windows, for the prompt), and a CLI that was found a moment ago and will not run now. The first names the surface that can answer — Chat in the browser — and the key that would answer here instead, and Chat passes that sentence through whole, as it already did for a CLI that is not installed or not signed in. The second says the CLI would not start and quotes what the machine said, and is worth trying again.
- **Setup diagnostics no longer ask for a key your Claude plan does not need.** With the Claude plan chosen as the model, the configuration check reported the connection as an error — "Profile 'anthropic' uses provider 'anthropic' at non-local URL but has no API key configured" — and told you to go and set one. That profile is served by the Claude CLI's own sign-in, so the finding is skipped while the CLI is installed. Without the CLI nothing can serve it, and the finding is the truth and stays.
- **The model menu names the engine that actually answers.** The menu asked the secret store whether a connection had a key, while the turn itself runs with the key the chat stream's own resolver puts on the profile — and for every provider but ChatGPT those are not the same thing. With an Anthropic key saved in Settings the menu therefore called the connection Anthropic's API while the Claude CLI was the thing answering. The menu now asks that same resolver, so the label and the engine cannot disagree. Separately, and older than this change: a key saved in Settings does not reach a chat turn at all, for any provider, because the field the resolver looks the stored key up by (`api_key_secret_name`) is not a field `ModelConfig` has. That is not fixed here; a key written into `thomas.toml` still works, and so does your Claude plan, which needs none.
- **One reader decides what a refused model call said.** Autopilot's pause read a plan name, a quota code and a reset time out of the error; Chat's failure text read nothing out of the same string, which is how the two surfaces described one limit in two ways. Both now read `thomas/core/provider_limits.py`, and the Claude CLI's not-signed-in and usage-limit wording moved beside it, so Chat and Build cannot spell the same refusal differently. Autopilot's pause text is unchanged.
