### Fixed

- **A plugin install that failed halfway left skills on disk that nothing could ever remove.** Installing an Agent Plugin performs five effects in order — copy the plugin tree, write its manifest, copy skills into the user's skills root, register MCP servers, and last of all write the installed record. Nothing wrapped them. So a failure at the fourth step left a plugin directory and a set of skills on disk while no record existed naming them, and `cleanup_agent_plugin_extras` reads exactly that record to know what to remove. The skills outlived the plugin permanently and no uninstall could reach them. Each effect now records its reversal the moment it succeeds, and any failure unwinds them newest-first, so a failed install leaves nothing behind. One thing rollback deliberately does not promise: a failed *reinstall* leaves the plugin uninstalled rather than restored, because the previous version's skills and MCP rows are removed before the new tree is copied — putting the old directory back would restore a plugin whose extras are already gone, which is a worse lie than a clean absence.

- **The desktop installer had the same defect, and now has the same fix.** `install_bundled_plugin` and `install_plugin_bundle_bytes` also copy the plugin tree and write the installed record last, and that record is the only handle anything has on the result: `uninstall_plugin` needs an id it can only read from a record, and `_prune_orphan_dependency_plugins` iterates records rather than the filesystem. So a failure in between left a complete plugin directory that nothing could list, name or remove. Both are wrapped now; `install_plugin_from_store` delegates to the second and is covered by it. Dependencies installed earlier in the same call are deliberately not rolled back — each wrote its own record, so they stay uninstallable by name rather than becoming invisible, and the existing orphan prune collects any the failed dependent was alone in requiring.

### Added

- **The kernel's undo stack turned out to work on disk too.** `thomas/server/install_transaction.py` is the same `DisposalStack` the kernel uses for event subscriptions and service registrations, applied to filesystem and registry writes. That was the test of whether phase 3.2's idea generalised past in-process state, and it did: reversals unwind in reverse order, one failing reversal never strands the rest, and rollback is idempotent. An install is now the same kind of object a mounted plugin is — something that knows how to undo itself.
