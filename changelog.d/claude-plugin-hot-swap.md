### Added

- **A plugin can be unplugged and replugged while Thomas is running.** `thomas/core/kernel/hotswap.py` adds the two operations the kernel was missing: `unplug` takes a plugin off and hands back a handle that can put it back in the same scope with the same config, and `swap` replaces one atomically. Before this, `dispose()` was the only way off and it also forgot the plugin, so "off for a moment" and "gone" were the same operation. Neither function awaits, so on the loop that runs a turn a swap is indivisible — no hook dispatch can land in the gap between the old plugin's subscriptions going away and the new one's arriving.

- **A supervisor holds every installed plugin by name.** `thomas/server/plugin_supervisor.py` replaces the one-shot boot mount at server startup: `unplug`, `replug`, `reload` and `sync`, plus a `status` that names what is mounted, what you switched off, and which plugins registered no hooks at all. `sync` mounts what was installed since, drops what was uninstalled, and reloads what changed on disk — and deliberately leaves alone anything you unplugged by hand, because an off switch a disk scan can flip back on is not an off switch.

- **Live plugin controls over HTTP.** `GET /api/plugins/kernel` reports the kernel's seams, the four plugin systems and the live runtime; `POST /api/plugins/kernel/{unplug,replug,reload,sync}` change it. All five require API access *and* loopback, the status route included: a reload imports Python from the plugins directory into the running process, so reachable from another machine it would be arbitrary code execution rather than a plugin toggle.

- **The other three plugin systems are kernel services.** `thomas/server/plugin_systems_kernel.py` mounts the extensions catalog and both installers as one-service kernel plugins — the default provider behind each lives in `thomas/server/plugin_system_providers.py` and is re-exported, so what a system *is* and how it gets mounted are separable but there is still one import site — so each is registered reversibly, listed by name and replaceable in place while Thomas runs. `thomas/server/desktop_plugins` resolves the installer service, which puts the live desktop-plugin install path through the kernel without the marketplace import route changing at all. Replacing a provider is an in-process call (`MountedSystems.swap`) and not an HTTP route — a provider is an object, not something a request can name — and `GET /api/plugins/kernel` now names the provider answering for each of the three, so a swap is something you can see rather than something you take on trust.

- **The marketplace reads its catalog and installs its bundles through the kernel.** `/api/marketplace/plugins` no longer imports `load_extension_catalog`; it resolves the `extension_catalog` service, so a provider swapped in while the server is answering requests changes what the next request returns. `POST /api/marketplace/import` resolves the `agent_plugin_installer` service and asks it both of its questions — does this installer claim the bundle, and install it — where it previously imported `bundle_is_agent_plugin` and `install_agent_plugin_bytes` directly. Those were the two services that had been mounted and swappable with no production caller at all, which made them a surface rather than a seam. `tests/test_marketplace_kernel_swap.py` proves both on one running aiohttp app: the catalog answers `1.0.0`, a provider is swapped, and the same client's next request answers `2.0.0`; a recording installer swapped in mid-flight reads back the config, the bundle bytes and the `source` it was handed. What was deliberately not done is making `agent_plugins_adapter.install_agent_plugin_bytes` a facade, the shape the desktop installer has — `tests/test_install_transaction.py` reads that function's source to check the install is transactional, so the seam belongs at the call site.

### Fixed

- **Editing a plugin had no effect until Thomas restarted, and nothing said so.** `thomas/plugins/runtime.py` cached loaded plugin instances against the mtime of `installed_plugins.json`. Editing a plugin's own code does not touch that file, so every load after the first returned the instance built from the code as it was at startup — for the life of the process. The cache key now includes a fingerprint of the plugins' source, and the fingerprint hashes file *contents* rather than timestamps: a filesystem with one-second mtime resolution reports no change for an edit made within a second of the load, which is exactly the shape of an agent editing its own plugin. Both bounds on that fingerprint are folded into the digest instead of applied quietly — a tree over the file cap is marked as truncated, and each file contributes its size as well as its first megabyte — so a bound cannot turn into `unchanged` about code that changed.

- **A reload could report success and run the old bytecode.** Plugins were imported through `SourceFileLoader`, which runs the cached `.pyc` whenever the source's mtime *in whole seconds* and its size both match the cache header. A rewrite within the same second whose length happens to match satisfies that exactly — the shape of an agent editing its own plugin — and the reload then reported `reloaded` while the previous version kept answering. Measured on the running app: `outcome: reloaded` thirteen times while the hook stamped `loop36` instead of `loop49`. Every plugin import now goes through `thomas/plugins/source_loader.py`, whose loader declines the cache entirely (`path_stats` raises, so `get_code` compiles from source and writes no `.pyc`), and whose `sys.meta_path` finder extends that to a package's own `from . import rule` — which the loader that imported the package does not resolve. The suite had not caught it because `tests/conftest.py` sets `sys.dont_write_bytecode`, while `python -m thomas.server`, `thomas serve` and the caged server's scheduled task all write bytecode: `tests/test_plugin_source_reload.py` runs with writing **on**, sets the stale-cache condition deterministically, and checks the trap itself so the rest cannot pass for the wrong reason, and `tests/test_plugin_reload_over_http.py` does the same over the reload route on a real app.

- **Every mount used to leave a disposed scope on the kernel root forever.** `Context.fork` puts `child.dispose` on the parent's stack so a child cannot outlive its parent, and nothing took that entry back off when the child disposed itself. About 410 bytes per mount, and a reload, a replug and a swap each mount again: the root's undo count rose 10 → 110 over 100 live mounts. A disposing scope now drops its own entry from the parent, and `seam_report` publishes the root's undo count (`root_effects`) so a stack that only grows is visible on the status route instead of being something you measure by hand.

- **A reload of a package would have silently kept the old submodule.** A plugin package is imported under a synthetic module name and its submodules land under that name. Re-executing the package `__init__` without clearing them re-binds the cached submodules, so an edit inside a submodule reloads into the old behaviour — worse than not reloading, because the log reports success. `purge_imported_modules` clears them first; a test pins it by editing only a submodule.

- **A second mounted plugin no longer cancels the first one's contribution.** Hook dispatch went through the bus's `emit`, which hands every subscriber the same payload and returns their answers side by side. Two plugins that each add to the same key therefore both worked from the *original* payload, and folding the results afterwards kept only the last one — with two plugins mounted, one of them silently did nothing. `Context.fold` threads the payload through the subscribers in turn, so each sees what the ones before it produced and a chain of plugins composes; `emit` keeps its fan-out shape for notifications. The bridge's legacy per-call scan had the same defect for the same reason and now folds between plugins too, so which plugins are heard does not depend on whether the host mounted them.

- **The agent-plugin installer service can answer whether a bundle is its own.** Its `accepts` imported the detector from `agent_plugins_adapter`, which has never exported that name — it imports four *other* names from `agent_plugins_manifest`, where the detector actually lives. Every call raised `ImportError`, and because nothing called it yet, nothing said so. It resolves the right module now and a test calls it on three bundle shapes.

- **A broken edit no longer unplugs a working plugin.** A reload whose new code raises leaves the previous version running and reports `failed`, and hands back the fork the restored version is running under so the caller does not hold a disposed handle to a live plugin. Asking again about a file that is still broken reports `failed` again rather than `unchanged`: the supervisor advances its fingerprint only where a mount, a replug or a swap actually succeeded, so the one word that means "the code on disk is already running" is never said about an edit that never got on the bus — whether it failed to import or imported and failed to mount. Fixing the file makes the next reload land with nothing else asked of you.

- **A reload that failed now says why, instead of blaming the wrong thing.** The runtime loader never raises — it logs a plugin's own import error at debug level and returns nothing — so the reason that reached the status surface was always "no recognizable plugin entrypoint on disk", said about a file that has a perfectly ordinary entrypoint and a typo on line 1. That sentence sends you looking for the wrong problem, and after a failed reload it is the only sentence you get. The loader now carries the real failure out — `ValueError: typo in my edit`, `SyntaxError: ...`, `get_plugin() raised ...` — and a test asserts the reported reason names the actual error for two shapes of broken edit.

### Changed

- **The marketplace catalog routes are four modules instead of one 1,190-line file.** `thomas/server/routes/marketplace_catalog_aiohttp.py` is 535 lines of request handling; what a field means moved to `marketplace_catalog_fields.py`, what a row looks like to `marketplace_catalog_rows.py`, how a pack is normalized and read off disk to `marketplace_catalog_packs.py`, and hosted sync plus the local fallback payload to `marketplace_catalog_sync.py`. Each imports only from the ones above it, so the layering is checkable by reading the import block. This was not housekeeping: the file was over the 800-line soft limit in `docs/monolith_guard_baseline.json` and that limit is enforced on every file a change *touches*, so the two-line change that put the agent-plugin install on the kernel could not be made at all until the file was smaller. `thomas/_architecture.py`'s `server` debt note claimed the file exceeds 1,020 lines; `tests/test_architecture.py::test_health_annotations` fails a debt note whose file has come back under the limit, so that clause is removed and nothing else in the protected file changed.

- **Server startup mounts the supervisor instead of the one-shot mount, and cleanup disposes both handles.** The supervisor and the three system services are two independent mounts and get an error handler each, so a failure mounting one cannot drop the other's handle: a mount the app has forgotten is still on the bus, with nothing left that can unwind it at cleanup and a status route that would call its running plugins unsupervised. Either mount failing leaves the server starting without that half; neither stops it from starting. Both mounts live in `thomas/server/plugin_startup.py` as two plain functions the startup and cleanup handlers call, so the contract can be checked without standing up sixty route families to reach a nested handler. Cleanup records what it has unwound in a set placed on the app at mount time and mutated in place, so running it twice unmounts nothing twice and one handle whose own `dispose` raises does not leave the other mounted — and cleanup writes no key to the app, because aiohttp freezes the application before `on_cleanup` runs and assigning to a frozen app is deprecated, once per teardown, about 907 times across the test files that build a real app. The one-shot `mount_installed_plugins` is gone: the supervisor replaced its only caller here, so it was a second way to mount plugins that nothing in the running app used, and its docstring named a CLI user that does not exist. `plugin_systems_report` resolves the extensions catalog *and* the agent-plugin installer through the kernel rather than importing them, and reports for each of the four systems whether it reached the kernel.
