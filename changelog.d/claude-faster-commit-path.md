### Changed

- The scoped commit tool runs its local gates two at a time by default (`THOMAS_COMMIT_GATE_WORKERS`, at most 8; `1` is the old one-at-a-time loop; the default was four until a performance review showed four per commit call does not scale to a fleet) and gives the verdict the serial loop gave: the first failing gate in registry order, with its output. Board readers wait for the gate that writes the board, the last inbox look stays last, every child starts without a console window, and a gate that never finishes is stopped after `THOMAS_COMMIT_GATE_TIMEOUT` seconds (default 600, `inf` and `nan` read as the default) and refuses. A gate stopped because an earlier one failed is killed, except `active_folder_guard`: it holds a lock file for a few milliseconds and a kill inside that window would leave every other agent's guard refusing for a minute, so it is left to finish and its result is thrown away. Gates that run at once first take one of a few machine-wide slots (half the cores, at least four; `THOMAS_COMMIT_GATE_SLOTS`, `0` for no limit), so ten agents landing together share the cores instead of starting forty gates. The 43 per-gate "is this script tracked" questions are one `git ls-files` (and a gate spelled `./scripts/x.py` or `scripts//x.py` is still the tracked gate it names), `enforcement_integrity` and `workboard_task_plans` read their blobs through one `git cat-file --batch`, the branch tip is read from the ref file or from `packed-refs` instead of a git process per probe, and `workboard_evidence` and `problem_closure` are left out only when the selection cannot reach what they read. A gate left out because its script is untracked is now named in the result's `gate_output`; the old tool built that sentence and dropped it. Measured with one agent (a dry run through all 44 real gates, one change: one source file and one new test): 21.1 s before and 6.9 s after, one sample each; a second review measured 33.6 s against 8.7 to 10.9 s on pure trees (3.4x, range 2.8x to 5.0x) on a busy machine. Those numbers were taken with four workers. With the default of two, one agent, a dry run of one small change, two samples each: 13.8 and 15.1 s against 29.5 and 33.7 s for the old tool (about 2.2x); one and four workers gave 14.4 to 16.0 s, so for one agent running gates side by side adds almost nothing.
- A landing that loses the race to another agent's landing rebases onto the new tip and tries again (at most three attempts, after a random pause of up to a second, `THOMAS_COMMIT_REBASE_JITTER`), instead of ending in `branch_race` and paying the whole ladder again. Every gate is judged again on the new base except two: `active_folder_guard` (the process scan, reused for 60 s inside the same landing) and `exception_handler`, whose pass is kept only against a fingerprint of everything it reads (the index entry and the base's entry of every selected path, the safety policy and its local overlay, the gate's own script and the one module it imports). A neighbour that changed the policy, a selected file edited between attempts, or a selected path the neighbour changed all make it judge again. An earlier version kept seventeen gates on a "the neighbour did not touch a selected path" rule; review showed that let through landings a fresh run refuses, so it is gone. A refusal from a gate that ran while the tip moved is judged again on the new base and is final if it comes back in the same words; a refusal at a stable tip is final at once, and one that keeps changing until the attempts run out is reported as that gate's refusal, not as a race. A branch that was rewritten rather than advanced is still `branch_race`. `THOMAS_COMMIT_LEGACY_PATH=1` gives the old behaviour for all of this: one attempt, nothing left out, nothing reused, one gate at a time.
- `workboard_agent_claim` and `workboard_changed_files` judge the staged set against the tip the temporary index was built on (`THOMAS_COMMIT_BASE`, set by the commit tool), not against a HEAD another agent's landing had just moved. The value is honoured only when `GIT_INDEX_FILE` is inside the commit tool's `thomas-agent-commit-*` directory, so one left in a shell cannot hide a staged revert. In the earlier ten-agent run those two refusals were 32 of 113 and 59 of 125 landing attempts.
- `--require-slot` (or `[landing_queue] require_slot = true` in `agent_safety.toml`) makes the commit tool refuse to land unless the caller holds the landing queue's slot, and says how to get one. It is off by default, a dry run never needs a slot, and it asks the queue through a small interface. The policy is read as committed and as it stands in the working tree, and either one saying true requires the slot, so an uncommitted edit can turn the requirement on for one landing and never off; a policy file that does not parse still requires a slot when it says so; a queue that fails in any way refuses instead of crashing. It is cooperation with the queue, not protection.

- Ten simulated agents landing together (one run per arm, same machine, indicative only): 27 of 28 landings in 692 s against 17 of 28 in 1088 s for the old tool, 2.5 times the landings per minute. A second review took most of that apart: about 2.2 of the 2.5 times comes from the batched reads, the base pin and the rebase, and only about 12 percent from running gates at once, which is why the machine-wide slots are in.
