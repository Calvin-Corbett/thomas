### Fixed

- **An ack now survives the board being reverted underneath it, so the inbox gate can tell the truth during a commit.** pre-commit clears unstaged changes before it runs any hook by checking the whole tree back out to the index, and the workboard ack writes `plans/thomas/WORKBOARD.md` without ever staging it. For the roughly forty seconds of a commit, every gate that read the board saw the pre-ack copy and reported already-read mail as unread — so acking did not help, retrying did not help, and the gate was made advisory to stop the treadmill. Measured three ways in a scratch repo driving a real pre-commit: an ack in a tracked-but-unstaged file is invisible to a hook, while the same ack under a gitignored path or in the index survives. The ack now also writes a read receipt under `runtime/coordination/inbox_receipts/`, which the checkout cannot reach, and `unread_messages` consumes it. That function is the single chokepoint all seven inbox consumers already funnel through, so the fix reaches the commit-path gate and the Bash adapter without either of those protected files changing.
- **A receipt heals the board, so the sender learns its message was read.** A receipt only the recipient can see is half a fix: the acking agent's gate would be correct while `--inbox`, the audit trail, the escalation clock and the sender were all still told the message was never read. Every ack now replays any earlier receipt whose board row is still open. Reconciliation writes, so it is called from the ack path and never from a gate read path — a gate that writes is a gate that can fail for a new reason.

### Changed

- **Read receipts are scoped to one board, not to an agent id.** Thomas runs a board per project root and the same agent id appears on all of them, so an agent-keyed receipt let an ack on one board mark a same-id message read on another. It also made every test that acks write into the real `runtime/` directory and poison the next test — which is how it was caught, by a batch that passed one file at a time and failed when run together. Receipts are keyed on the resolved board path plus `(msg_id, created_at)`, so a receipt can never suppress a different message that happens to reuse an id.
- **A receipt that cannot be written never fails an ack that already succeeded.** The receipt is a durability aid; if the store is unwritable the ack still lands on the board and behaviour degrades to exactly what it was before. A coordination tool that adds a new way to fail is a worse trade than the problem it solves.
