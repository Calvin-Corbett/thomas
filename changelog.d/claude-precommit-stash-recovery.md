### Added

- **Work that a failed commit destroyed can be recovered from pre-commit's own stash.** A commit that fails a gate does not simply stop. pre-commit clears unstaged changes before it runs any hook and restores them afterwards, but where a hook's auto-fixes conflict with what it stashed, its recovery re-checks-out the tree and re-applies; when that second apply also fails, the edit survives only inside the patch pre-commit wrote. `git status` then reports the file unmodified, so the loss reads as "nothing changed" rather than as damage, and the retry destroys the next attempt too. Seven edits went that way in one session on 2026-09-09, and the cause was misdiagnosed twice as another agent rewriting the tree. `scripts/forge/precommit_stash.py` lists those saved patches, says which of them hold work the tree is missing, and puts one back. It is deliberately not a hook — nothing in it runs during a commit, because a recovery tool that adds a new way to lose work is not a recovery tool.
- **Recovery works in the case that actually loses work, not just the easy one.** Applying the stash as a diff is tried first, since when it succeeds it is exact and touches nothing else. In the failing case it cannot succeed: the hook rewrote the same file and staged the rewrite, so the diff no longer matches either the tree or the index. The patch does not depend on either — its `index <old>..<new>` line names the pre-image blob, so each file is rebuilt from that blob in a scratch repository and copied back. Whatever gets displaced is kept beside the file as `<name>.pre-restore`, and `--restore --dry-run` reports the whole plan without writing any of it. Against this machine's real cache the dry run rebuilt twenty-nine files from one stash, recognised twenty-eight as already present, flagged the single divergence, and left the working tree byte-identical.

### Fixed

- **The step that decided whether lost work could be recovered had been overwriting it.** An earlier draft of the same tool tried `git apply --3way` before falling back, and reported "nothing was changed" when it failed. `--3way` implies `--index`: on a partial merge it writes conflict markers into the working tree and stages what it merged before returning non-zero, so the backup taken immediately afterwards captured a conflicted file instead of the content it existed to preserve. Plain `git apply` verifies every hunk before writing anything and was the only safe probe all along. The test that caught it asserts the displaced content equals what was there beforehand; asserting merely that a backup file exists would have passed on the corrupted version.
